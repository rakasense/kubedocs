The problem without a controller

  • Process crashes → who restarts it?
  • Node dies → who reschedules?
  • Traffic spikes → who scales?
  • New image → who rolls it out safely?
  • Bad release → who rolls it back?

Desired vs Actual state

Kubernetes is a reconciliation engine. You describe what you want — controllers make it true.

// desired
3 replicas · image:v2 · cpu=500m
// actual
2 replicas running · 1 crash-looping
controller reconciles

"The system continuously closes the gap between what you asked for and what is running."

02 · landscape

Kubernetes Workload Landscape

Pick the right primitive for the right job
03 / 22
// kubectl api-resources

Pod

Smallest deployable unit. One or more co-scheduled containers sharing network and volumes.

Deployment

Stateless app with rolling updates and rollbacks. Owns a ReplicaSet.

StatefulSet

Stable identity + per-pod PVCs. Databases, queues, clustered software.

DaemonSet

Exactly one Pod per node. Agents, log shippers, CNI, monitoring.

Job

Run-to-completion. Batch, migrations, one-shot data jobs.

CronJob

Time-scheduled Jobs. Backups, reports, reindexing.

ReplicaSet

Maintains N pod replicas. Almost always owned by a Deployment.

Supporting

Service · ConfigMap · Secret · PVC · HPA · PDB · NetworkPolicy · Ingress · ServiceAccount.

04 · deployment

Deployment

The default workload for stateless services
05 / 22
// selector is immutable · template is the engine

Important spec fields

  • replicas — desired count
  • selector — immutable; matches template labels
  • template — Pod spec owned by RS
  • strategy — RollingUpdate | Recreate
  • rollingUpdate — maxSurge / maxUnavailable
  • resources — req drives scheduling, limit caps
  • probes — readiness gates rollout
  • topologySpread — spread across zones/nodes
apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  replicas: 3
  selector: { matchLabels: { app: web } }
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    metadata: { labels: { app: web } }
    spec:
      containers:
        - name: app
          image: ghcr.io/acme/web:1.4.0
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "500m", memory: "256Mi" }
          readinessProbe:
            httpGet: { path: /healthz, port: 8080 }
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/zone
          labelSelector: { matchLabels: { app: web } }

Operate

kubectl explain deployment.spec
kubectl get deploy web -o yaml
kubectl scale deploy/web --replicas=5
kubectl set image deploy/web \ app=ghcr.io/acme/web:1.5.0
kubectl edit deploy/web
kubectl rollout status deploy/web

07 · stateful

StatefulSet

Stable identity, stable storage, ordered rollout
08 / 22
// DNS: pg-0.pg.default.svc.cluster.local

Why it exists

  • Stable identity — pg-0, pg-1, pg-2
  • Stable storage — per-pod PVC via volumeClaimTemplates
  • Ordered rollout — up & down in order
  • Headless Service — DNS A-records per pod

Use for

PostgreSQL · MySQL · MongoDB · Kafka · ZooKeeper · etcd · Elasticsearch · Redis cluster.

# Headless Service for stable DNS
apiVersion: v1
kind: Service
metadata: { name: pg }
spec:
  clusterIP: None
  selector: { app: pg }
  ports: [{ port: 5432 }]
---
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: pg }
spec:
  serviceName: pg
  replicas: 3
  selector: { matchLabels: { app: pg } }
  template:
    metadata: { labels: { app: pg } }
    spec:
      containers:
        - name: postgres
          image: postgres:16
          ports: [{ containerPort: 5432 }]
          volumeMounts:
            - { name: data, mountPath: /var/lib/postgresql/data }
  volumeClaimTemplates:
    - metadata: { name: data }
      spec:
        accessModes: [ReadWriteOnce]
        storageClassName: gp3
        resources: { requests: { storage: 10Gi } }

Operate

kubectl get statefulset pg
kubectl get pods -l app=pg -o wide
kubectl get pvc -l app=pg
kubectl scale sts pg --replicas=5
kubectl rollout status sts/pg
kubectl delete sts pg

Pods: pg-0 · pg-1 · pg-2 — and PVCs data-pg-0..2.

08 · node-level

DaemonSet

One Pod per node — node-level workloads
09 / 22
// one Pod per node · survives node drains

When to use

  • Log shippers (Fluent Bit, Filebeat)
  • Node agents (Datadog, node-exporter)
  • Networking (CNI plugins, kube-proxy)
  • Storage daemons (ceph, glusterd)

Node selection

nodeSelector or nodeAffinity to target GPU / SSD / Linux-only.

Taints & tolerations

DaemonSets tolerate node taints so they can run on every node (including control plane).

apiVersion: apps/v1
kind: DaemonSet
metadata: { name: fluentbit }
spec:
  selector: { matchLabels: { app: fluentbit } }
  updateStrategy:
    type: RollingUpdate
    rollingUpdate: { maxUnavailable: 1 }
  template:
    metadata: { labels: { app: fluentbit } }
    spec:
      tolerations:
        - key: node-role.kubernetes.io/control-plane
          operator: Exists
          effect: NoSchedule
      nodeSelector: { kubernetes.io/os: linux }
      containers:
        - name: fluentbit
          image: fluent/fluent-bit:2.2
          resources:
            requests: { cpu: "50m", memory: "64Mi" }
            limits:   { cpu: "200m", memory: "128Mi" }
          volumeMounts:
            - { name: varlog, mountPath: /var/log }
            - { name: varlibdockercontainers,
                mountPath: /var/lib/docker/containers,
                readOnly: true }
      volumes:
        - { name: varlog, hostPath: { path: /var/log } }
        - { name: varlibdockercontainers,
            hostPath: { path: /var/lib/docker/containers } }

Operate

kubectl get ds
kubectl get pods -l app=fluentbit -o wide
kubectl rollout status ds/fluentbit
kubectl set image ds/fluentbit \ fluentbit=fluent/fluent-bit:2.3
kubectl logs -l app=fluentbit --tail=100
kubectl delete ds fluentbit
09 · batch

Job · CronJob

Run-to-completion and time-scheduled work
10 / 22
// Forbid concurrencyPolicy prevents overlap

Job semantics

  • completions — required successful pods
  • parallelism — pods allowed at once
  • backoffLimit — retries before Failed
  • activeDeadlineSeconds — kill switch
  • restartPolicy — OnFailure | Never

CronJob adds

  • schedule — 5-field cron
  • concurrencyPolicy — Allow | Forbid | Replace
  • historyLimits — keep last N succeeded/failed
# Nightly Postgres backup
apiVersion: batch/v1
kind: CronJob
metadata: { name: pg-backup }
spec:
  schedule: "0 2 * * *"
  timeZone: "UTC"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 300
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: pg-dump
              image: postgres:16
              command:
                - sh
                - -c
                - pg_dump -Fc -d "$DB" \
                   -f /backup/dump-$(date -u +%Y%m%dT%H%M%SZ).dump
              envFrom:
                - secretRef: { name: pg-credentials }
              volumeMounts:
                - { name: backup, mountPath: /backup }
          volumes:
            - name: backup
              persistentVolumeClaim: { claimName: pg-backup-pvc }

Operate

kubectl get cronjobs
kubectl get jobs -A
kubectl create job manual-pg --from=cronjob/pg-backup
kubectl logs job/manual-pg
kubectl delete cronjob pg-backup
kubectl delete job -l job-name=manual-pg

The six levers

  • requests/limits — drive scheduling and prevent noisy neighbors
  • HPA — scale replicas on CPU/memory/custom metrics
  • PDB — guarantee N pods during voluntary disruptions
  • topologySpreadConstraints — even spread across zones/nodes

17 · the mental model

Kubernetes Controller Pattern

Observe · Compare · Reconcile · Repeat
18 / 22
// the heartbeat of Kubernetes

The reconcile loop

Desired State — what the spec says
↓
Observe — watch cluster state
↓
Compare — diff desired vs actual
↓
Reconcile — drive actual toward desired
↓
Update — write back to API
↓
Repeat

Why this matters

  • Controllers are level-triggered, not edge-triggered — state, not events, is the source of truth.
  • Every Kubernetes component follows this pattern: Deployment, ReplicaSet, StatefulSet, DaemonSet, Job, CronJob, Garbage Collector, Service controller.
  • Operators extend Kubernetes by writing their own controllers (CRDs + reconcile loops).
  • Idempotency is the contract: calling reconcile N times has the same effect as calling it once.

The promise

"If I keep my desired state correct, the system will continuously close the gap to it."

  • Job controller · CronJob controller · Garbage collector
  • Service controller · EndpointSlice controller · Node controller

Anatomy of reconcile()

# Pseudocode — every controller looks like this
func Reconcile(ctx, key) {
  obj := informer.Get(key)         # 1. read current state
  desired := buildDesired(obj)     # 2. compute desired state
  diff := diff(desired, obj)       # 3. compare
  if diff == empty {
    return Done                  # 4. nothing to do
  }
  err := apply(ctx, diff)          # 5. mutate cluster
  if err {
    enqueue(key, retry)            # 6. retry with backoff
  }
  requeueAfter(time.Minute)        # 7. periodic safety re-sync
}

Why operators exist

A CRD declares a new kind. A controller implements Reconcile() for it. That is the entire extension model of Kubernetes — Helm is a package, an Operator is a controller.
